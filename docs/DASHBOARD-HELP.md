# Dashboard help

The header question-mark button is present for every signed-in role. It opens a local, Arabic operational guide. Asking a question opens the closest source-reviewed article; related results and per-section browsing remain available. This is local search over reviewed text, not a generative AI integration. No question history or external model requests are stored/sent.

`dashboard-help-data.js` contains 93 workflow/account articles (including the 49 system accounts explained in the accounting guide), plus a generated exact-label field registry. Every navigation tab has an article or a linked workflow. An article explains meaning, rationale/relationships, ordered prerequisites, the responsible team, and destinations. It does not assert that a specific record has a particular defect based on question text. Newly created custom accounts and unknown fields are explicitly outside the static glossary; the UI asks the user to consult the workflow/responsible team rather than inventing a value.

`dashboard-help.js` uses the existing `SSMPDSearchDestinations.catalog/open` permission checks. Financial destinations recheck roles/grants on click. Restricted destinations display the responsible team rather than granting access. Inventory navigation uses the existing accounting/inventory renderer; reception settings use a narrow navigation helper that loads the destination workspace and checks its current manager permission before opening settings. The help feature does not expand the management pilot or change booking writers.

“فحص إعدادات الحجز الحالية” explicitly invokes the existing `receptionCatalogIssues()` RPC for accounts allowed to see accounting and reception. The existing RPC checks finance/workspace access and refreshes derived catalogue state. Returned service/package/contract issues are escaped and linked to their original setup sections. This scan does not prove doctor availability, balances or stock readiness. Empty/error states state the limit. Requests cannot update another article, a closed panel or a changed account. No new RPC, migration, approvals or business records are created by this change.

The field registry covers 1,031 source definitions and 815 distinct labels from 63 modules. `scripts/help-field-inventory.cjs` reads literal HTML labels/placeholders/ARIA labels, typed field configurations, and field/select helper calls using the TypeScript parser. `scripts/build-dashboard-help.py` contains reviewed explanations, source-specific distinctions and explicitly reviewed placeholder aliases. It produces `dashboard-help-fields.js` and the coverage manifest `docs/dashboard-help-fields.json`; `--check` rejects source additions without reviewed text or stale generated files. This coverage is tied to this source revision, not a promise about user-created/future fields.

Field matching now also uses the current form's known static heading and prefers narrower section definitions. The original form's input values are not read. Examples: ledger account kind versus message kind; patient weight versus KPI weight; stock units versus medicine intervals; archive visit number versus package visit order. Direct questions can find field explanations as well as workflow articles.

Each existing dialog receives “شرح النموذج”. Help snapshots field labels, required flags and names; it removes controls/options before extracting labels and never reads values. Labels associated by sibling layout, ARIA references or translation markers are recovered as well. Approved source placeholders cover unlabelled controls. Hidden controls are omitted. Long forms are not truncated at 60 fields and have a local field filter and count. Required/read-only/disabled status and existing format constraints appear alongside the explanation. Named dynamic clinical controls (lab/radiology/chronic conditions/session treatments/meal completion) receive workflow-specific selection guidance. Unknown future labels keep an explicit fallback. The overlay traps keyboard focus, restores prior inert/aria/body-scroll state, supports Escape, and disposes on shell rebuild/logout. It cannot navigate away from an open dialog. Edited inline forms require the user to save first and explicitly acknowledge navigation.

## Maintaining the guide

When a screen's labels, rules or prerequisites change, update its article and field groups in the same PR. Use the actual code/database guards as source. Never embed operational data, patient names, identifiers, approved contract terms or secrets in the public static guide. Explain physical quantity/unit conversions explicitly. Maintain independent review, event-based posting, non-negative cash and distinction between collection and revenue.
