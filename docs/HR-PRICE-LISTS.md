# Human resources and price lists

Updated import, canonical service identity, contracting placement and calculated-payroll behavior is documented in [CONTRACT-PRICE-IMPORTS-PAYROLL.md](CONTRACT-PRICE-IMPORTS-PAYROLL.md). The sections below describe the initial release and its original limitations.

## Shared records and authorization

`human_resources` provides employee and collaborating-doctor profiles, canonical account/doctor/payroll key links, departments/branches/managers, dates, emergency contacts and HTTPS document references. Only managers, super admins or accounts explicitly granted `has_hr_access` manage personnel. Other active accounts get their own linked profile and can request leave, permission, overtime, training or an advance. They cannot browse other people. HR access does not grant financial access.

Leave credits and leave requests affect the calendar-year balance only after a different authorized reviewer approves them. Attendance is manually entered with planned and actual times and independently reviewed. Times are entered in the device timezone and displayed in Cairo time. Attendance, lateness and an advance request never create a payroll deduction or payment. Monthly attendance can be exported. Authorized HR/financial creators can prepare a monthly payroll request from an existing approved employment contract. The form shows approved attendance, lateness and leave requests for review, requires documented allowances/tax/insurance/advance recovery inputs, and sends the request to the original financial command with its original approval and duplicate-month guards. It neither pays nor posts an approved salary directly. Existing payroll and doctor-contract buttons route to the original accounting screens under their original permissions. Doctor and payroll keys are selected from existing contracts, never inferred from names. HR manager cycles and stale profile edits are rejected.

This release does not calculate a batch payroll from attendance, connect a biometric device, upload HR attachments, or implement fixed-session/guaranteed-minimum doctor compensation. Document references use existing protected HTTPS locations. It does not create actual profiles for current employees automatically. Existing financial contracts and balances remain authoritative. HR task/performance buttons open the existing authorized modules rather than copying records.

## Pricing and reception

`price_lists` provides dated, versioned center and contract price lists. Modes are fixed prices, discounts and mixed. Missing services explicitly use the center price, the list discount, or are blocked. Item percentage discounts and list percentage discounts apply sequentially, then both fixed discounts per service unit. A new list replaces the old entity-contract discount; it is not silently stacked. A flag controls additional operational discounts, enforced by a trigger on reception orders. Existing approval requirements for operational discounts remain in place.

Drafts are saved by their creator, submitted, and approved by a different price-list manager. Approved records are immutable. Clone creates a new draft version; termination keeps history. Approval rejects overlapping active periods for the same center/contract scope. Entity-list dates must be inside an active parent contract. A price list does not expand the parent contract's selected services or patient eligibility. Egyptian pounds remain the accounting currency.

The canonical reception catalog calls the same resolver as the preview calculator. Center prices flow into service versions and package calculations. Contract prices flow into existing operational entity contracts. Price evidence is included in operational versions and quote snapshots. Existing invoice snapshots are not rewritten, doctor contract terms are not changed, and existing supply inclusion comes from the original service BOM. New service versions can be generated on the next catalog synchronization, even when prices remain unchanged, to record evidence.

Local Excel/CSV imports use code/name/price/percentage/amount columns. Text PDFs are read locally for candidate rows. All imported rows remain an editable preview, unmatched services require explicit selection, and saving still requires independent approval. PDF extraction is not a completeness guarantee; scanned/image PDFs need conversion first. No raw source file is uploaded to Supabase. Preview calculates only approved lists, not unsaved drafts.

## Migration and verification

Three migrations were applied via the Supabase connector and filenames use its generated versions. The telemetry-producing CLI path previously rejected by approval review was not rerun. Tables are in non-exposed private schemas with RLS and revoked direct access. Authenticated RPC definer execution is intentional and internally checks the actual admin/role/grant. Anonymous execution is revoked. A trigger protects the new grant flags from invite-claim privilege escalation.

`tests/hr-price-lists-sql.cjs` uses the actual migrations and reception bridge in PGlite. It verifies HR identity/self scope, optimistic locking, annual leave balance, independent approvals, attendance, grant protection, immutable prices, overlap rejection, entity coverage, legacy-discount separation, real canonical catalog prices/evidence, additional-discount enforcement and no payroll postings. `tests/hr-price-lists-dom.cjs` verifies card collapse, financial permission separation, failed-form preservation, service-key saves and a calculation without writes. Existing admin-workspace and head-nursing tests pass.

Production read-back in a rolled-back authenticated-owner transaction confirms the new workspaces return successfully and anonymous command execution is denied. It confirms zero actual HR profiles and zero new price lists, so no operating prices have been switched. No real task, patient, employment contract, salary, doctor contract, approval or payment was created for testing. The broad smoke still has its pre-existing social-tab-count failure and requestAnimationFrame warning. Public `tests/hr-price-lists-fixture.html` uses synthetic data; it is not evidence of a real employee login.
