# حزمة تطبيق العقود الإلكترونية على الإنتاج — جاهزة، **لم تُطبَّق**

الملف: `supabase/migrations/20261109110000_online_contracts.sql` (PR #380). إضافي بالكامل: 4 جداول جديدة + دوال جديدة. **مفيش جدول أو دالة موجودة بتتعدّل** (كل `update`/`insert` جوه الملف على الجداول الجديدة بس). الواجهة تشتغل قبل وبعد التطبيق (قبله مابتعرضش حاجة).

## ملخص للمالك (يُقرأ قبل الموافقة)
لو وافقت، هيتضاف نظام العقود الإلكترونية للأطباء: الحسابات تبعت العقد المعتمد للدكتور، والدكتور يفتح «عقدي» يقرأ النص والجدول ويوقّع بإصبعه أو بالقلم على التابلت (أو يرفع صورة توقيعه) ويضغط أوافق أو يرفض بسبب. نص العقد ونص إقرار المسؤولية المهنية تعدّلهم إنت من الشاشة (تعدّل المقدمة وتضيف وتشيل بنود)، وكل تعديل بيبقى رقم نسخة جديد، وكل موافقة بتتسجل برقم النسخة اللي الدكتور شافها مع صورة توقيعه. النصوص الموجودة دلوقتي مسودات مؤقتة **مش بتظهر لأي دكتور** لحد ما تنشر النص اللي المحامي يوافق عليه. ومفيش حاجة بتتمنع: لا الاستحقاقات ولا الشغل، لحد ما إنت تحدد تاريخ بداية لكل قاعدة (عقد غير موقّع / عدم الإقرار)، والافتراضي «غير مفعّل». التطبيق نفسه ثواني ومفيش جدول حالي بيتلمس، وفي ملف تراجع جاهز.

## 0) قبل التطبيق (للي هيطبّق — المالك/ChatGPT؛ Claude Code ملوش وصول للإنتاج)
1. Pre-check (قراءة فقط) — كل الصفوف لازم `true`:
   ```bash

   ```
2. نسخة احتياطية احتياطية (الملف إضافي فمش بيمسح حاجة، لكن للأمان):
   ```bash
   mkdir -p ~/claude-work/backups
   ~/claude-work/bin/swnw-sql "select * from clinic_finance.doctor_contracts" > ~/claude-work/backups/doctor_contracts-before-online-contracts-20261109.json
   ~/claude-work/bin/swnw-sql "select p.id, p.admin_id, p.doctor_key, p.status from clinic_people.people p where p.doctor_key is not null" > ~/claude-work/backups/people-doctor-links-before-online-contracts-20261109.json
   ```
3. تأكد إن PR #380 متدمج في `main` والـCI أخضر، وإن الواجهة المنشورة فيها `finance-contract-signature.js` و`my-contract.js` (الواجهة بتتجاهل غياب الـmigration فمفيش ترتيب إجباري).

## 1) التطبيق (بعد موافقة المالك فقط)
```bash
~/claude-work/bin/swnw-sql -f supabase/migrations/20261109110000_online_contracts.sql
```
الملف جواه `begin … commit` وبيفشل بالكامل (ولا يطبّق نصه) لو أي شرط ناقص، وبيرفض لو اتطبّق قبل كده («تم تطبيق هذا الملف من قبل»).

## 2) التحقق بعد التطبيق (قراءة فقط) — كل الصفوف `true`:
```bash
~/claude-work/bin/swnw-sql -f docs/online-contracts-verify.sql
```
بعدها يدويًا من الواجهة (حساب المدير المالي): تاب الأطباء ← بلوك «نصوص العقد الإلكتروني» ظاهر، «تعديل النص» شغال. **لا تنشر ولا تبعت حاجة لحد ما المحامي يوافق على النص.** تاريخ البداية يفضل فاضي.

## 3) التراجع (لو احتجناه)
```bash
~/claude-work/bin/swnw-sql -f supabase/rollbacks/20261109110000_online_contracts.rollback.sql
```
بيرفض تلقائيًا لو فيه طلبات توقيع أو موافقات مسجّلة (سجلات موقّعة لازم تتصدّر الأول، وبعدين يتحذف يدويًا بقرار منك). لو مفيش سجلات: بيشيل الدوال والـ4 جداول بالكامل ومفيش أثر على الجداول القديمة.

## ما اتجرّب (offline، بدون أي اتصال بالإنتاج)
- **بروفة Docker**: Postgres 16.15 (`postgres:16-alpine`) في حاوية مؤقتة `--network none`، اتحذفت بعد التجربة. اختبار الـSQL الكامل (`tests/online-contracts-sql.cjs`: إرسال، موافقة دكتور بتوقيع مرسوم/مرفوع، رفض ملفات غير صالحة، صلاحيات، idempotency، تبطيل النسخة القديمة، تعديل النص بالبنود والمسودات، تواريخ التطبيق، rollback ثم إعادة التطبيق) نجح على Postgres حقيقي بدل PGlite.
- **بروفة التراجع**: التطبيق ← التراجع ← لا يبقى أي أثر (0 كائنات متبقية) ← إعادة التطبيق ← تراجع ثانٍ: حالة المخطط مطابقة تمامًا للدورة الأولى. التراجع يرفض فعلًا لو فيه سجلات.
- الـpre-check قبل التطبيق = كله true؛ بعد التطبيق البنود 6-8 تتحول false (يعني بيكشف التطبيق المكرر)؛ والـverify بعد التطبيق = كله true.
- ما لم يُجرَّب: البيانات الحقيقية للإنتاج (مفيش وصول)؛ فرق بين الـfixture وإنتاج Supabase الفعلي (أدوار anon/authenticated حقيقية موجودة فيه، والـpre-check بيتحقق من الاعتماديات).
